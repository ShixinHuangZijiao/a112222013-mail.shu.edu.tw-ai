## 二、輸出欄位契約

| 欄位名稱 | 型別／限制 | 用途 | 畫面標籤 | 如何查原文 |
|---|---|---|---|---|
| `company_and_title` | str，必填，不可空白 | 確認是哪間公司的哪個職缺 | 公司與職稱 | 找原文開頭或標題的公司名與職稱 |
| `responsibilities` | list[str]，必填，可為空清單 | 判斷工作是否符合興趣 | 工作內容 | 每一項都要能在原文找到對應句子 |
| `requirements` | list[str]，必填，可為空清單 | 判斷自己是否符合資格 | 應徵條件 | 對照原文的條件、科系、技能 |
| `location_and_schedule` | str，必填；沒寫填「未提供」 | 判斷能否配合通勤與課表 | 地點、時數與期間 | 地址、時段、日期要與原文一字不差 |
| `salary` | str，必填；沒寫填「未提供」 | 比較待遇 | 薪資／津貼 | 數字與單位要與原文相同，不可換算 |
| `how_to_apply` | str，必填；沒寫填「未提供」 | 知道下一步怎麼投、何時截止 | 應徵方式與截止日 | 信箱、截止日要與原文相同 |
| `missing_info` | list[str]，必填，可為空清單 | 列出應徵前要問的問題 | 原文沒寫、建議先問的事 | 每一項都應是原文確實沒寫的資訊 |

## 三、測試紀錄

| 項目 | 實際輸入／操作 | 實際輸出／錯誤 | 人工判讀與修正 | 證據類型 |
|---|---|---|---|---|
| 空白 | API 關閉，空白直接按「整理職缺」 | 「請先輸入要處理的原文。」 | 正確，未送出請求 | 離線（AppTest） |
| 過長 | 輸入 6001 個字 | 「請縮短到 6000 字元以內；不會默默截斷原文。」 | 正確，未送出請求 | 離線（AppTest） |
| 正常資料 | `sample_data/正常職缺_虛構.txt` | 未測 | 待逐欄查原文 | 真實 API／未測 |
| 資訊不足 | `sample_data/資訊不足職缺_虛構.txt` | 未測 | 待確認有無編造薪資、地點 | 真實 API／未測 |
| 結果保存／再送出失敗 | 模擬成功結果後，再送出空白 | 舊的 7 個欄位消失，只顯示「請先輸入要處理的原文。」 | 舊結果有清除 | 模擬（假 client，非真實 API） |
| 缺 key／服務失敗 | 啟用 API 但沒有設定 `OPENAI_API_KEY` | 「缺少 OPENAI_API_KEY，請設定本機 .env 或平台 Secrets。」 | 在送出請求前停止，假 client 呼叫次數為 0 | 離線（AppTest） |
| 模型拒答 | 模擬回應帶拒答標記 | 「模型拒答；請調整資料或任務。」，沒有顯示欄位 | 不保存結果 | 模擬（假 client，非真實 API） |
| Cloud 部署（必做） | 未部署 | 未測 | 未測 | 雲端真實API／未測 |

另以離線方式確認 SDK 會送出的 strict Schema：7 個欄位都在 `required`，`additionalProperties` 為 `false`。

真實 API 每筆補：測試日期、模型、完整虛構原文、實際 JSON／畫面結果、人工核對與實際請求數。
同一情境的修正前後用同一筆資料比較；不預設改 prompt 必然改善。不要用固定假回應填「真實 API」。
未測項目寫未測；請求失敗如實記錄，不捏造成功紀錄。真人瀏覽器／部署與程式模擬分開標示。
正常／資訊不足兩筆可直接在雲端完成，不必本機再重複呼叫；至少一筆須為雲端真實API成功。若追加測試，須另計請求數。
